# 骑行对话需求与证据状态

接口在原有 `contextIntent`、`placeContext` 外返回 `requirementState`。客户端在同一对话的下一轮原样回传该字段，切换会话时保存和恢复；新对话清空。旧客户端仍可只传原有字段。上下文由客户端保存，不是可信的服务端持久化记录，也不作为候选事实或规划授权的独立凭据。

`requirements` 覆盖起终点、途经点、偏好、避让、里程和时间等字段，每项含 `value`、`status` 和 `priority`。没有信息标记 `unknown`，模型识别或新修改的内容标记 `pending`，只有用户确认后且该值确实包含在确认摘要中才标记 `confirmed`；未修改且值一致的已确认项可跨轮保留。要求优先级为 `required`、`preferred` 或 `unspecified`，路段标签的 `tagPriorities` 逐项区分必须和偏好，明确模型判断需用户确认；规划校验方式详见 `agent-route-comparison.md`，不能验证的条件不视为已满足。

模型遗漏、输出 null 或空数组不会自动清空已有要求。明确取消时模型通过 `clearedFields` 指定字段；明确修改为 false 或空值通过 `changedFields` 指定。用户开始新路线时清空旧条件。距离或时间上下限相互矛盾时阻止确认并提示调整。客户端状态会按服务端允许的字段和值重新构建；候选事实只取本轮真实检索结果，先前 ID 如未重新检索只标为 `reference_only`，不携带未经核实的事实。候选被选中后仍为待确认，确认时重新读取有效记录后才标记确认。

确认摘要会标注默认的当前位置和骑行时间范围。名称相似不表示实际位置、路线风景或道路安全已核实。

## 对话中的需求检查与修改（第四阶段）

路线对话会展示当前骑行需求及其已确认、待确认或默认状态；面板可折叠并独立滚动。出发地、目的地、目标区域、距离、时间和骑行体验可以直接编辑或清除。途经顺序、路段属性及避让要求通过对话修改，避免以不完整的结构化字段替换复杂条件。

结构化修改只接受允许的字段，检查数值范围与上下限关系，并保留其他条件。修改后需要重新确认；已有路线标明基于旧条件。正在等待必要选择时，修改一般字段不会自动回答该问题；若候选地点尚未选定，须先完成选择再修改目标区域，以免旧候选与新区域混淆。目标区域变化时，未选定的旧检索上下文会被清除。

`npm run eval:idea` 使用真实模型和固定候选数据、模拟规划器，并在多轮中传递 `requirementState`。该评测适合回归需求理解和工具选择，不能证明真实数据库、高德导航可用性或路线质量；实际服务需要单独做端到端检验。现有单元测试覆盖修改保留其他条件、等待问题时不规划、字段校验和必需约束无法验证时的处理。

一次使用上海模拟位置的真实服务抽样中，沿江候选可检索，但首个候选不符合 30 公里目标；绕圈和补给场景各生成了一条路线，本次没有找到备选。必须避开爬坡时，系统因无法核实连接道路而要求用户调整约束。另一个包含完整路段名称及 20 公里上限的请求中，模型把名称开头误判为出发地，最终未能验证距离上限：确认摘要仍需用户核对，该案例不应计为通过。以上为单次抽样而非稳定性统计，不能推断所有路段属性、补给点或道路的实际质量。
