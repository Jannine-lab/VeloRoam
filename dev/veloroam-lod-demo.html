VeloRoam · 移动端克制显隐原型

克制不是"显示几个"，是 立场 —— 敢替用户做决定

移动端核心只有一句话：「给你一条现在就骑的路」。默认屏（L0）只服务这句话： 一条主推路线、起点、一行推荐理由、两三张备选卡。Strava 段 / POI / 热力图不是"图层"， 是模式——一个手势进入，退出即消失。下面的开关就是两种立场的现场对比。

1诊断：为什么你始终找不到平衡点

因为你把"克制"当成了数量旋钮，在 96→72、70→50 之间反复横跳——那是同一个坑。 真正的克制是立场：你一边想"推荐"，一边不敢替用户决定， 于是用"多显示一点"来缓解"漏掉重要东西"的焦虑。平衡点不在那个数字里， 在你对每个要素回答"我是替用户决定，还是让用户自己决定"的那一刻。

2架构：L0 强推荐 · L1 一招手 · L2 可搜索

大多数人以为克制 = "把 L0 做小"，于是砍来砍去总觉得亏。 真正让 L0 敢变小的，是 L1 够不够近。做不到"一个手势可达"的要素， 才会被迫堆在默认屏上。先修可达性，克制就自然发生。

L0 · 默认屏 —— 你自信推荐的：1 条主推路线 + 起点 + 推荐理由 + CTA
L1 · 一个手势 —— 不常驻、但一键召唤：路段雷达 / 补给 / 备选切换
L2 · 可搜索 —— 不显示、但找得到：全量列表 / 搜索 / 历史

3判据：三轴决定"该不该默认显示"

对每个要素问三个问题，而不是问"显示几个"。平衡点是三者的输出，不是独立输入的参数：

  • 置信度 —— 我有多确信它对"此刻这个人"是对的？低 → 不默认显示，但可召唤。
  • 缺失代价 —— 藏起来而他需要，后果多严重？错过补给 = 严重 → 永不真正隐藏。
  • 任务态 —— 他在逛 / 在骑 / 在找店？同一要素在不同状态价值天差地别。

4授权：打分 = 隐藏的通行证

你费大劲写的 routeScorer / rawScore / routeRelevanceScore， 意义不是"排好序展示"，而是给你有权隐藏低分项的资格。 一个分数就是一句"我有资格替你判断"的声明。把低分项全摆出来，等于白打了分—— 打分系统的终极产出，是一张允许你隐藏一切的通行证。

5机制：图层模态化，不常亮

桌面端屏幕大、可以容忍常驻图层；移动端克制 = 图层模态化（进入 / 退出），而不是常亮。 Strava 段、POI、热力图都不是图层，是"模式"。这一刀砍下去，平衡点瞬间清晰—— 你不是在"隐藏信息"，你是在重新安排谁替用户做决定。

6操作：动手试试

  • ① 切开关 —— 同一批数据在"全摊开"与"克制"下的现场对比。
  • ② 点地图上的路段 —— 进入聚焦态，其余全部退到背景（0.15）。
  • ③ 点底部芯片 —— 路段雷达 / 补给：一个手势召唤 L1，退出即消失。
  • ④ 点"换一条" —— 备选卡把另一条路线升为主推，虚影变实。
  • ⑤ 看理由行 —— 一行"为什么推荐"，是克制换取信任的锚。
这是交互原型（零依赖、可离线双击打开），不是真实地图数据。设计要点：L0 强推荐 + L1 一个手势可达 + 图层模态化 + 三轴判据 + 打分即隐藏授权。 对应真实代码中的 getMinScoreForZoom / getHotPointDisplayMode / dimAllOtherSegments 的演进方向。
